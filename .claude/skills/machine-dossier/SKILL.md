# 機種深堀り分析（ドシエ）の作り方

対象は**稼働貢献週が8週以上の機種**（1本目のSAO2はちょうど8週）。**8週に届かない機種は対象外**——スコアの①②③を8週目に揃えて測るため、8週未満だと同じ物差しに載せられない。「なぜ生き残ったのか」を数値と中身の両面で確定させる長文分析。
2026-08-19、1本目（スマスロ ソードアート・オンラインⅡ）を作り切る過程で確立した手順。
場所と構成の設計理由は memory `project_machine_dossier_tab` / 5軸は `project_machine_eval_5axes`。

## 置き場所

| ファイル | 役割 |
|---|---|
| `src/machineDossiers.json` | 本文データ。`{updatedAt, dossiers:[…], common:{criteria, glossaryBase}}` |
| `src/MachineDossier.jsx` | 描画。図・レーダー・稼働グラフのコンポーネント |
| `src/App.jsx` | 分析タブ内のモード「深堀り分析」（コラムの隣） |

**カギは既存の認証を使う。**分析タブは `@key-cre.co.jp` のGoogleログイン必須（`toAdmin` が他ドメインを即サインアウト）なので、
新テーブル・RLS・GRANTは不要。強さはフロント判定までで、本文はJSバンドルに載る。

**Artifact版も同じ内容で並行して持つ**（社外共有・大画面用）。サイト版だけ直してArtifactを忘れる事故を今日2件出したので、
`scripts/misc/check_dossier.py` が両者の差分を検査する。**片方だけ更新して終わらせない。**

## 手順

### ① 対象機種を決める

```bash
# 貢献週8週超で、まだ生きている（直近が100%超）機種を出す
python scripts/misc/update_sis_record.py --dry      # 書き込まずに sisRecord の差分を見る
```
`src/machineAnalysis.json` の `sisRecord`（貢献週／設置週／死に台週数／直近稼働値）で判断する。

### ② SIS実数値を集める

- **機種名はDBの表記と完全一致させる**（例 `Lソードアート・オンラインII` / `L戦国乙女5業火を穿つ宿焔の双刃` / `Lからくりサーカス2`）。
  **部分一致で拾ってはいけない**——「スロット ソードアート・オンラインⅡ」で引くと初代SAO（169週・貢献17週）が混ざる事故を出した。
  対応表を手で書いて突合する。
- **稼働値 = 1台あたりアウト ÷ その週の全国平均アウト（実値）× 100。**分母は必ず `sis_national_daily` の週内日次平均。
  詳細は skill `sis-national-real-value`（部分集合の単純平均を「全国」にしてはいけない）。
- `sis_weekly_data` はページング必須（PostgRESTは1000行で頭打ち）。`order` は**一意キー**にする（`week_start.asc,machine.asc`）——
  不安定なORDER BYでlimit/offsetすると行が重複する。
- 貢献週は `sis_machine_stats` の公式値を使い、自前計算で上書きしない。
  **公式の貢献週は設置週数より1週少なく出ることがある**（集計ラグ）。これは説明不要な既知事項なので本文に書かない。

### ③ 5軸で測る（すべて8週目に揃える）

```bash
python scripts/misc/dossier_axes.py --list        # 8週以上ある機種の一覧
python scripts/misc/dossier_axes.py "<DB上の機種名>" --interest <YouTube上位20本の累計> --interest-pct <n> --dmm <点> --dmm-pct <n>
```

| 軸 | 指標（8週目に固定） | 揃えられるか | 母数 | ウェイト |
|---|---|---|---|---|
| ① 需要 | 8週目の稼働値 | ✓ | 185機種 | **35%** |
| ② 持続 | 8週目の総稼働 ÷ 2週目の総稼働 | ✓ | 185機種 | 20% |
| ③ 総稼働 | 8週目の稼働値 × 平均設置台数＝「全国平均の台◯台分」 | ✓ | 185機種 | 20% |
| ④ 関心度 | YouTube上位20本の累計再生（経過週を併記） | ✗ | 11機種 | 15% |
| ⑤ 納得感 | DMM評価点（スロットのみ・評価30件以上） | ✗ | 12機種 | 10% |

**5軸で固定する（2026-08-20 決定）。**6軸目を置けるか候補を全部測ったが、
**軸に値する独立な次元が今のデータには無い**ことを確認した（下記）。

**すべて全国平均で割った相対値で測る。**生のアウト・枚数・円はお盆や年末に全機種いっせいに上がるので、
導入時期がそこに当たった機種が得をする。②の持続率も総稼働ベースの比にする。

**①と③は似て見えて別物。**①は「1台がどれだけ熱いか」、③は「市場全体でどれだけの量を担っているか」。
SAO2は①3位・③14位で**薄い設置（4台）で熱い型**、Lミリオンゴッドは①32位・③6位、
L甲鉄城のカバネリは①14位・③3位で**厚い設置で量を稼ぐ型**。この差は台数比では出ない。

**ウェイトは実測で決めて固定する。**貢献週を目的変数にした重回帰（185機種）で
**①単独 R²=0.441** → ①+③ 0.469 → ①+②+③ **0.487**。

**スコアは予測モデルではない。**生死は①でほぼ当たる（①②③は相互相関0.69〜0.96）。
5軸は**「どういう台か」を1枚で示すため**のもの。この区別を本文にも書く。

#### 試して外した候補（同じ検討を二度しない）

| 候補 | ①②③との重複 | 同値 | 増分R² | 外した理由 |
|---|---|---|---|---|
| 出玉率の週次ブレ（荒さ） | 0.18 | 2% | ±0.000 | 最も独立だが**「荒い＝良い」の向きが決まらない**＝外側＝上位のレーダーに載せられない |
| 初動の高さ（初週の稼働値） | 0.59 | 1% | +0.014 | ①と半分以上重複 |
| 底の高さ（最も低い週） | 0.95 | 1% | +0.036 | ①の測り直し |
| 初週を超えた週数／ピーク週 | 0.32／0.36 | **94%** | +0.017／+0.021 | ほぼ全機種が初週ピーク＝差が出ない |
| コイン単価 | 0.24 | 1% | — | **ホールの設定次第**で台の性格ではない（ユーザー指摘） |
| 出玉率の水準 | 0.28 | 2% | ±0.000 | ホールの調整と客の引きが乗る |
| 初週の設置台数 | 0.71 | 6% | +0.018 | ③に含まれる |
| 相対粗利 | 0.54 | 1% | +0.002 | 単独r=+0.47だが**①の言い換え** |
| パネル内シェア | — | — | +0.031 | 分母のパネルが週で**4〜127機種**と動き週をまたいだ比較が不能 |
| 競合の新台圧 | 0.13 | — | +0.001 | **生死とほぼ無関係**（r=−0.12）。新台は毎週一定ペースで出るので窓による差が小さい |
| ③台数比（8週目÷初週） | 0.57 | **25%** | +0.021 | 増台は2ヶ月以上かかるので8週では動かない（ユーザー指摘） |
| ③台数比（直近÷初週） | — | — | — | 上位が80週・141週の機種＝**経過週の長さを測っていた** |
| ②4週目÷初週の稼働値 | — | 1% | +0.001 | 窓が3週間しかなく、初週のご祝儀が分母に入る |
| ④週あたり再生数 | — | — | — | 動画は導入直後に集中投稿＝**経過1週の機種が最上位**に来る |

**6軸目に一番向いているのは介入度**（gameDesignLibrary の `presentation.intervention`・0〜3）。
稼働データの外にある台そのものの性格だから。ただし**確定台×付与が現在25件で母数不足**。
**40件を超え既存軸との相関を上回ったら昇格**という条件を先に固定してある（後から閾値を探さない）。

**取れない軸は「測定不能」にする。**推測で埋めない。ウェイトを分母から外して残りへ再配分
（⑤が測定不能なら分母90%）。レーダーは `values` に `null` を入れると**その軸だけ形が欠ける**。

- ⑤は母集団の切り方だけで33〜54まで動く（スロット12機種=33／全31=48／100件以上13=54）。
  母集団は**スロットのみ・評価30件以上**に固定する。
- 関心度で**取れないものは取れないと書く**：他サイトのPV（非公開）・5chのスレ数（JS描画で機械取得不可）・
  YouTube検索ヒット数（機種名の一般性で桁が変わる。北斗124万件 vs うみねこ2は1,633件）。

### ④ 解析値は2サイト以上で突合する

`memory/sources_and_rules.md` の有力サイト一覧（ななプレス／ちょんぼりすた／スロベース／こぜログ／一撃／DMMぱちタウン／P-Summa）。

- **天井・設定差・特化ゾーンの数値は最低2サイト、食い違うなら5サイトまで広げる。**
  導入前の予想値がそのまま残っていることがある（SAO2で「999G天井」「CZスルー6回目」が5サイトすべてで裏取りできず訂正）。
- 突入契機・自力契機は**実機解析で裏を取ってからURLを出典に書く**。
- **前作・シリーズ前機種の記述が混ざりやすい**（SAO2で初代の「アルヴヘイム・オンライン」を書いてしまい訂正）。
  解析ページのURL末尾の機種IDを見て、どの機種のページかを毎回確認する。

### ⑤ 参考動画を集める

```bash
python scripts/misc/fetch_youtube_clips.py "%TEMP%/clips.json" "機種名 特化ゾーン名" "機種名 設定6" "機種名 天井" ...
```

- **チャプター・概要欄のタイムスタンプ・ヒートマップはいずれも取得できない**ので、「◯分◯秒が見どころ」は書けない。
  かわりに**短尺の切り出し（10分以内）を先頭グループに置く**——切り出しそのものが見どころなので時刻がいらない。
- 長尺は**再生数の多い順＝実質の定番**として目的別に並べる。尺・チャンネル・再生数はすべて実取得値で、取得日を書く。
- **全URLを oEmbed で生存確認する**（`https://www.youtube.com/oembed?format=json&url=…` が200か）。
- タイトル先頭一致でマッチングすると**同じシリーズの別動画に化ける**（機種名の接頭辞が長いため）。
  videoId で確定させるか、一致後に必ず一覧を出して目視する。
- 本数は多くてよい。ただし**「①の数本だけで仕組みは掴める」入口を作る**こと。

### ⑥ 7章で書く

大見出しは**全機種で統一**。中見出し以下は機種固有。

| 章 | 名前 ／ 副題 | 固定範囲 |
|---|---|---|
| Ⅰ | 総合評価 ／ 結論と5軸スコア | 中見出しまで固定 |
| Ⅱ | 指標と基準 ／ 稼働値・貢献週の定義／5点評価が使えない理由 | **内容ごと共通**。`{"t":"common","v":"criteria"}` で参照 |
| Ⅲ | 稼働データ ／ 週の推移・全国順位・同期他機種の比較 | 中見出しまで固定（数値だけ差し替え） |
| Ⅳ | 台の仕組み ／ 図解と用語集 | 図は機種固有。用語集は `common.glossaryBase` ＋ 機種固有をマージ |
| Ⅴ | ゲーム性の分析 | 機種固有（見出し自体が機種の性格を表す） |
| Ⅵ | 市場の声と予測 | 機種固有 |
| Ⅶ | 資料 ／ 参考動画と出典・データ注記 | 固定 |

- **全章 `closed:true`（既定で全部畳む）。**
- 副題は**中身の列挙**にする。狙いの説明やアピール文にしない。
- セクション型: `part` `h`(lv2/lv3) `p` `note` `kpis` `steps` `table` `bullets` `quotes` `voices` `videos` `links` `fig` `chart` `radar` `glossary` `common`
- 本文パーサは `**強調**` と改行だけ。HTMLは書かない。
- `chart` は **DBから毎回その場で計算**するので、週次データが更新されれば本文を触らず数字が最新になる。
  `machine` 名がDBにヒットするかを push 前に curl で確認する。
- 評価は `ColumnFeedback` を `columnId="dossier_<id>"` で流用（コラムと同じGOOD/BADが `column_feedback` に入る）。

### ⑦ 文体（ここで格が決まる）

- **わかりきったことを書かない。**「ちょうど倍」「これが駆け抜けと呼ばれる状態」「設置9週なのに貢献8週なのは集計ラグ」——
  全部不要。読者が知っていることの説明は品位を落とす。詳細は memory `feedback_no_obvious_restatement`。
- **自分の比喩を機種の仕様として書かない。**「残量ゲージ」と書いたが実機にそんな表示はなく、比喩が仕様に化けていた。
  事実（差枚数管理である）を書き、そこから優位性を展開する。
- 「核心：」「〜の解剖」「〜の正体」のような引っぱる前置きを使わない。
- 数字は必ず出典と母数をセットで書く。**「低い」「高い」は分布を測ってから言う。**
- 話が飛ぶところは箇条書きにして定義を先に置く（13週 vs 20週の議論は「貢献週の基準」として5段階に整理した）。

### ⑧ 公開前チェック（両方パスするまで push しない）

```bash
python scripts/misc/check_svg_layout.py src/MachineDossier.jsx <Artifact版html>
python scripts/misc/check_dossier.py
```

- `check_svg_layout.py`: 図のテキストが枠・viewBoxから出ていないか（全角1.0em/半角0.55emで幅を見積もる）。
  図を作ったら**必ずスクショでも目視する**——重なりは幅チェックだけでは出ない。
- `check_dossier.py`: ①撤回した表現の残存 ②サイト/Artifactの見出し差 ③common参照の解決 ④図と用語集の整合
  ⑤章構成と折りたたみ状態 ⑥主要数値の片寄り ⑦動画（重複URL・メタ欠け・Artifact反映） ⑧表の幅と貼り付け事故 ⑨表の行のサイト/Artifact突合
- 新しい事故を出したら**このチェッカに1項目足してから直す**。今日は⑦⑧⑨をこの流儀で追加した。

### ⑨ Artifact版は生成する（手で直さない）

```bash
python scripts/misc/gen_artifact_regions.py     # 表・スコアカード・KPIを生成
python scripts/misc/gen_dossier_blocks.py       # <!-- gen:NAME --> で囲んだ節をまるごと生成
python scripts/misc/sync_dossier_prose.py       # リード文・順位表・予測などの散文を同期
```
スコアカード・KPIタイル・5軸表・ウェイト表・③のnote・持続率表は**サイトJSONが唯一の正**で、
Artifact側はここから生成する。同じ箇所を手で3回直して食い違いを出したので、以後は生成に切り替えた。
図・本文の散文は手書きのままなので、`check_dossier.py` の突合で守る。

## やってはいけないこと

- 共通部分（Ⅱ・共通用語）を機種ごとにコピーする → 基準がドリフトする。`common` に1回だけ置く。
- 部分一致で機種を突合する／`sisRecord` を自前計算で上書きする。
- 5点評価だけで「評価が低い台」と書く（分布を測る・母集団を固定する）。
- ③を「直近÷初週」で測る（経過週の長さを測っているだけになる）。
- ④を「週あたり」に正規化する（経過1週の機種が最上位に来る）。
- ウェイトを機種ごとに変える。
- 取れなかった数値を推測で埋める・出典URLを捏造する。
- サイト版とArtifact版の片方だけ更新して終わる。
- 1本目が固まる前に他機種へ展開する（memory `feedback_depth_first_one_at_a_time`）。
